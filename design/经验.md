# 经验：这次是怎么把地形和人物识别搞准的

> 配套：`设计思想.md`（为什么要这么想）、`状态总线.md`（具体怎么落地的）。
> 本文记的是**教训**——每条都来自 2026-08-19 这轮实测,附当时量到的数字,
> 免得下次又靠"感觉不对就调阈值"绕一圈。

---

## 零、最反直觉的一条

**模型一个都没换,也没重训。**

怪还是 `monster_v19.pt`,地形还是 `super_brain_v13_merged.pt`,
输入的原始检测框跟之前一模一样。变准的是**从"观察"到"状态"的那一层**,
外加两个把感知本身憋死的具体 bug。

所以下次再出现"识别不准",第一个问题不应该是"是不是要重训 / 换模型 / 调 conf",
而是:**模型到底输出了什么?那个输出是怎么被用掉的?**
这轮六个问题里,只有一个（怪的 conf 门槛）沾边模型,其余五个都在使用侧。

## 一、可测量的关系,不要写成常数

参考名牌图匹配是三条玩家定位路径里**唯一能回答"这是不是我"**的一条
（另外两条只能回答"这里有个玩家"）。它实测 **0/28 帧命中**,静默死了很久。

原因是一行常数：

```python
REF_SCALE_BASE = 0.85   # 实机名牌约为参考裁剪的 0.85 (在 768 高参考帧上标定)
```

这个 0.85 不是物理常数,它是**"这张名牌图" 和 "这个窗口尺寸" 之间的关系**。
后来用 `capture_nametag.py` 重采了一张名牌,真实尺度变成 1.00 ——
常数就在那一刻失效了,而且**没有任何报错**：

| 尺度 | 匹配峰值 | 结果 |
|---|---|---|
| 0.85（常数） | 0.562 | < 阈值 0.60,永远不命中 |
| 1.00（真值） | 0.676 | 命中 |

于是身份判定悄悄退化成兜底路径的"选屏幕上最靠下的名牌"——**谁站得低谁就是我**。

**教训**：一个数如果描述的是两个可变对象之间的关系,就别把它写成常数,
把它**量出来**。改成启动时全帧多尺度扫一次取峰值最高的尺度,窗口尺寸变了自动重标,
连续 90 帧不命中也重标。0/28 → 26/28。

**识别方法**：看到常数,问一句"它依赖什么?那东西会变吗?"
`REF_SCALE_BASE` 依赖名牌图和窗口;`FEET_TO_CENTER=35` 依赖角色贴图（基本不变,可以写死）。
前者必须测,后者可以写。

## 二、派生量必须和它依赖的东西同频更新

地形模型为了帧率每 `TERRAIN_EVERY=3` 帧才跑一次,平台存在世界坐标里跨帧融合——
这套设计本身没问题。问题是**相机位姿 `world_offset` 只在跑地形的那一帧更新**。

走路时镜头每帧滚动约 35px,中间两帧完全没人补偿。受控平移实验（平台中心误差）：

| | 地形帧 | 中间帧1 | 中间帧2 | 均值 | 最坏 |
|---|---|---|---|---|---|
| 修前 | ~1px | 35px | 71px | 35.8px | **75.5px** |
| 修后 | ~1px | 0.6px | 1.0px | **0.9px** | 4.0px |

而"到平台边缘"的容差是 `WALK_EDGE_MARGIN=25`,抓梯子 `ROPE_GRAB_DX=30`,
判断脚下 `SURFACE_TOL_Y=30`。**75px 是容差的 2~3 倍**。

所以现象是"地形识别不准",真相是**每次检测都是对的,只是被放在了 75px 之外的位置**。
决策层看到的是幻影平台:该转身的地方不转,以为脚下有台阶其实是空的。

**教训**：`screen = world - offset` 这类派生关系,只要 `offset` 更新频率低于消费频率,
中间那些帧消费的就是**过期的世界**。要么把消费降频（不可能,决策要实时),
要么把 `offset` 提频。

提频不一定要更多算力:相机位移是可以**直接测**的,不必等模型。
320×180 缩略图上一次相位相关,**2ms/帧**,精度 −34.8 vs 真值 −35,静止 40 帧零漂移。
地形模型继续每 3 帧做绝对纠正,相位相关只负责中间帧的相对跟随——
一个管精度,一个管频率,各司其职。

## 三、身份是实体的属性,不是每帧的选美结果

原来的玩家定位是:每帧在画面里找所有名牌候选,选"最靠下"的那个当自己。
屏幕上同时站三个人时,**每帧都可能换人**,于是待机不动时玩家坐标乱跳 300px。

这就是 `设计思想.md` 那句"上下文不能碰瓷对象身份"的具体形态:
一帧画面是 evidence,不是 identity。

**教训**：把定位器降级成只产 **observation**(位置 + 来源 + 分数),
采不采信交给实体自己(`PlayerState.observe`)按连续性判定:

- 小位移(≤60px)直接提交
- 中等位移:分来源——`ref`（验证过"是我"）直接采信,`badge`（只是"有个人"）要两帧一致
- 大位移(>260px)默认拒绝,但连续 4 帧落在同一处就翻案（换图/传送是真的）
- 连续 3 帧"看得见却不采信" → 强制采信（错的多半是我们自己的陈旧坐标）

这里有个来回调过两次的平衡点,值得记下来：

- **太松**：`ref` 命中就无条件 commit → 一帧锁到隔壁那个人。
- **太严**：`ref` 和 `badge` 一视同仁 → 实测某帧 ref 以 0.805 分找到真人在 216px 外,
  被两帧规则拒掉,位置冻在错的地方直到 LOST 超时,那 4 秒 bot 是瞎的。

分界不在距离,在**这个观察回答了什么问题**。能回答"是不是我"的,给它更大权限。

## 四、为掩盖 bug 而放松的阈值,会变成下一个 bug

战士模板里两个补偿:

```json
"filter_conf": 0.12,          // 原因: 怪老是"不进射程"
"attack_range_buffer": 80     // 原因: "玩家中心有 ~80-100px 抖动"
```

注释写得很诚实,都是为了补偿**玩家定位不准**。定位修好之后,补偿就变成纯噪声:
`filter_conf=0.12` 放行的 22 个低分框里 9/10 是杂物——树冠、蘑菇装饰、
传送门光柱、**鼠标指针**、甚至**自己的宠物花蘑菇仔**。
传送门光柱距玩家 281px,落在 `patrol_chase_range=360` 内,会把巡逻方向拽向传送门。

收到 0.35 后剩下 122 个检测全是真猪,代价是丢掉 1 个落在射程内的低分真猪（被树挡住）。

**教训**：调阈值补偿别处的 bug,等于把 bug 存进了配置。
存的时候一定要写清楚"补偿的是什么",并且**根因修掉后回来收**。
这次能收回来,全靠模板 JSON 里那几行 `notes_combat` 老老实实写了原因。

顺带:`attack_range_buffer: 80` 我没动,因为没有实机的真实近战距离数据。
它现在只影响 hold 滞回（打的过程中猪走远了别急着松手）,危害有限,但它仍然是一笔待还的账。

## 五、别把检测噪声当成结构

现象:bot 会**无故下跳**(↓+Alt)。而站在最底层按下跳是**空动作**,看起来就是原地抽搐。

根因不在下跳这个动作,在地形层认定"下面还有一层"的判据:

```
'down' 边: 玩家表面 y=392(宽 2000000) → 目标平台 y=396,高度差 4px
```

**4 像素被当成了一层楼。** 两个因素叠加:

1. v13 常漏检地面层,所以玩家踩的是"隐含地面"节点——它宽 2000000px,
   在 x 上与画面里**每一块**平台都重叠,重叠判据形同虚设。
2. `_edge()` 只要求 `yb > ya`,没有最小落差。跨帧融合出的几像素抖动就够了。

于是 34 帧里有 4 条这种假 'down' 边,其中一条只差 4px。

**教训**:几何判据里的"不等于"要写成"差得够多"。
凡是拿检测结果比大小的地方,阈值必须大于**该量的观测噪声**——
这里 `MIN_DROP_DY=50` 就是照着表面判定容差 `SURFACE_TOL_Y=30` 加融合抖动定的。
`yb > ya` 这种写法等于声称"检测是精确的",而它从来不是。

修完之后 4px / 35px 的假层消失,剩下 56px、51px 两条是真落差。

顺带按需求把下跳整个换掉了:改成**走出平台边缘自然落下**。
理由是它在任何情况下都安全——下面真有平台就掉下去,没有就只是往前走了两步;
而下跳在判断错的时候是纯粹的空动作。真正需要"穿过正下方单向平台"的图,
把模板的 `combat.allow_jump_down` 打开即可(默认关)。
这也是个更一般的取舍:**当判据可能出错时,选一个出错代价更小的动作。**

## 六、积分器必须有锚点 (挂久了才发作的那一类)

上一节修完当天就发现:**挂久了地形到处乱飘,不如刚开始的时候。**

每帧相位相关测出的位移是 −34.8,真值 −35 —— 单帧只差 0.2px,看起来完全可以接受。
但 `offset += 位移` 是个**积分器**,同向的微小偏差会线性累积:

```
0.2px/帧 × 7fps = 1.4px/s ≈ 84px/分钟
实测 400 帧后 offset 漂了 104px
```

偏差从哪来?一是位姿用整数累积,每帧 `round()` 把小数丢掉(同号,必然累积);
二更根本:整幅画面做相位相关时,**不动的东西会把估计拉向 0** ——
合成实验里是 `BORDER_REPLICATE` 的静态边条,实机里是视差背景(远景比前景滚得慢)。

但真正让人看出毛病的不是 offset 本身。offset 和实体是**一起**漂的,
所以理论上 `screen = world - offset` 会抵消。坏就坏在**实体有年龄**:

- 刚开始:所有实体漂移都是 0 → 一致 → 看起来很准
- 挂一小时:老实体带着 30px 的历史漂移,新实体带着 80px → **同屏画出来就散了**

实测屏幕坐标误差从 1.3px 涨到最大 **93px**,而且忽大忽小 —— 这就是"到处乱飘"。

**教训**:任何靠增量累积维持的量,都必须有**周期性的绝对锚点**,
否则误差没有回归机制。而这里锚点其实一直都在——地形模型每 3 帧给的检测是精确的,
只是我们没用它来锚:`BLEND=0.7` 的平滑每次只纠正 30%,而漂移是几十像素且持续同向,
30% 永远追不上。

修法是把**平滑抖动**和**纠正漂移**分开:

```python
resid = |检测中心 - 实体中心|
b = 0.0 if resid > SNAP_PX else BLEND     # 大残差 = 漂移 → 直接对齐
                                          # 小残差 = 抖动 → 继续平滑
```

400 帧长跑:均值 10px / 最坏 93px → **均值 1.8px / 最坏 8.5px**,
且第 400 帧和第 50 帧一样准,不再随时间增长。

**这类 bug 的特征**:短测试全绿,跑几分钟才发作,而且是"越来越差"而不是"一直差"。
所以验证长期运行的东西,**测试必须跑够长**——我最初那轮 12 帧的实验完全测不出来。

## 七、一个阈值别同时承担"起批"和"维持"

现象:**周围明明检测出怪了,但不稳定,bot 就是不打。**

两处叠加:

1. 决策消费的怪要求 `miss_frames == 0`(这帧必须看见)**且**连续确认 ——
   等于把可打率压成检出率的**平方**:

   | 每帧检出率 | 决策层"可打"帧占比 |
   |---|---|
   | 70% | **50%** |
   | 80% | 63% |

2. 更狠的是 `seen_frames` 一漏检就归零。于是一只稳定 50% 闪烁的怪
   **永远凑不齐连续两帧,永远确认不了** —— 站在猪群里说"没怪"。

而检测器在阈值附近抖动是常态:实测 12% 的检测落在 0.25~0.50 带,
其中一半在 0.35 门槛上下横跳。

**教训**:一个阈值不要同时回答两个问题。雷达那套 track-before-detect 分得很清:

- **起批门槛**(高):这是不是一个**新**目标?→ 杂物拿不到两次高分,永远起不了批
- **维持门槛**(低):这个**已知**目标还在不在?→ 真怪掉到 0.2 也不丢

对应到实体层就是三条:确认过就**保持确认**(不因一帧漏检撤销身份)、
允许短暂 **coast**(3 帧 ≈ 0.4s,用最后已知位置)、弱检测只能维持不能新建。
再加一条防滥用:只靠弱检测最多续命 1s,否则怪死了旁边一个树冠能把轨迹续到天荒地老。

| 每帧检出率 | 修前可打率 | 修后 |
|---|---|---|
| 50% | 24.5% | **94.0%** |
| 70% | 49.9% | **99.2%** |
| 80% | 62.7% | **99.8%** |

而只有低分的杂物:1000 帧里被确认 **0** 次。

顺带发现的连带问题:coast 期间镜头在动,怪的屏幕坐标不跟着动就会错位 ——
3 帧 × 35px ≈ 105px,已经超过近战射程 120px 的大半。所以第六节那个相机位移,
不只要喂给地形,也要喂给怪。喂了之后匹配也更稳:否则 `MATCH_DIST=80` 的预算
先被相机位移吃掉一大半,走得快时同一只怪会被判成新目标 → 身份跳变 → 攻击承诺被打断。

## 八、随机化治不了"没有目标"

现象:巡逻**左摇右晃不像人**。

第一次修:把固定 3s 翻向改成 6~15s 随机承诺 + 单步随机 + 偶发停顿/折返。
跨度从 375px 涨到 1374px,数字好看多了 —— 但用户看一眼就说"还是左摇右晃"。

他是对的。因为**问题从来不是节奏太规整,是根本没有目标**:

```
相机跟着玩家走 → 屏幕坐标里玩家几乎不动
→ bot 不知道自己在地图哪里、走过哪里
→ 除了"计时器翻烧饼"没有别的可做
```

在这个前提下,随机化只是把节拍器换成了不规则的节拍器。人不是随机走的,
人是**看一眼地形,挑一个远处的落脚点,一路走过去**。

修法是给它一个目标,并且目标要存在**世界坐标**里:

```python
world = screen + camera_offset      # camera_offset 是第六节为地形做的那个位姿
```

有了世界坐标,"那边平台的尽头"才是一个镜头怎么滚都钉得住的点。
选点就是"看地形":候选 = 平台左右端点 + 梯子上下端,得分 = 距离,
同方向加权(防到了就掉头),刚去过的打折(防在一处反复刷)。

| 版本 | 60 秒跨度 | 行为 |
|---|---|---|
| 固定 3s 翻向 | 375px | 原地小幅来回 |
| 6~15s 随机承诺 | 1374px | 幅度大了,仍是翻烧饼 |
| **目标驱动** | **2465px** | 走到右端 → 折返走到左端 → 再折返 |

一个意外的好处:候选只是**当前可见地形**的端点(半屏远),但走到之后新地形进入视野,
新端点更远 —— 自然形成"一路走到地图尽头"的连续推进,到头了最远候选变成反方向,
自动折返。**不需要全地图先验就能扫图。**

**教训**:当行为"不像人"时,先问它**缺的是纹理还是结构**。
缺纹理(节奏太规整)加随机化有用;缺结构(没有目标/不知道自己在哪)加随机化只是
把问题摊薄。区分方法很简单:**问它"你现在想去哪"——答不上来的,就是缺结构。**

## 九、同一个事实只能有一个真源

日志里刷屏的 `[ATTACK] Monster × 0 击`,根因是**射程判定有两份**:

- 决策层用 `engage + buffer(80)` 判"在不在射程"
- 执行层用 `engage` 判"够不够得着"

两个函数,结论能相反 → 决策发 attack、执行打 0 下、返回、决策再发 attack,10Hz 空转。

同一个毛病还有第二个形态:`is_in_attack_range(key="bullet")` 的默认参数。
战士的 bullet 射程是 0,所有**忘了传 key** 的调用（滞回锁定、巡逻的"进范围就停"）
对战士恒为 `False`,静默失效——战士走路永远不会因为"打得到了"而停,只能撞上去或超时。

**教训**：判定收成**唯一入口**,射程从模板算(`engage_range_x = max(近战, 远程)`),
调用方不需要知道自己是什么职业。滞回 buffer 只用于"**保持**攻击",绝不参与"**进入**攻击"。
然后用测试把不变量钉死:

```
凡是 is_in_attack_range(t) 为真的目标, is_in_attack_range(t, hold=True) 必为真
（决策放行的,执行一定够得着）
```

同一类还有:决策/执行/移动层原来各自加锁散读世界状态,读到的是**三个时刻**的世界。
改成一次决策冻结一个 `WorldSnapshot`,同一 `seq` 内所有判断自洽。

## 十、别把"我没实现那个动作"写成"目标不可达"

现象:人卡在下层平台来回蹭,上层的怪不去打。

代码里的结论是 `is_reachable = False` —— 看起来像是"地形不允许"。
但实测 458 个这样的目标,落差只有 30~140px,**一跳就能上**。
真正的原因是兜底启发式写着 `dx <= 150`:它默认"跳"就是原地起跳,
所以要求怪必须在头顶正上方。而上方的怪普遍在 260~520px 外。

**缺的不是可达性,是"先走到它下面再跳"这个动作。**
代码却把这份缺失表达成了"目标不可达",于是:

- 决策层信了,改去巡逻
- 巡逻又把这只怪设成目标(它在 chase 范围内),走到正下方就算"到达"
- 到达 → 换目标 → 怪还在 → 又设回来 → **在下层平台原地来回蹭**

一个能力缺口,伪装成地形结论之后,变成了一个看起来完全无关的死循环。

还有更深一层:**地形检测本来就不可靠**(v13 常漏检平台,那 60 例上方怪一个平台都没检出来)。
所以"没检测到梯子 → 够不着"是从**否定证据**推结论 —— 这是最容易错的一步。
怪站在上面这件事本身,就是"那儿有个能站的地方"的正证据,比我们没看见梯子更可信。

改法:起跳点取**怪的正下方**(不依赖平台检出),落差在 [单跳, 单跳×2] 之间时
**先去试跳**,跳不上由几次失败学到。试一跳的代价是 0.5 秒,
而错判"够不着"的代价是整只怪 —— 又一次"当判据可能出错时,选出错代价更小的动作"。
60 例 → 6 例 → **2 例**,剩下两例落差 284/286px,是诚实的够不着。

**教训**:`UNREACHABLE` 这类结论必须能回答"为什么"。
所以新的 `MovePlan` 带一个 `reason` 字段,日志里直接写
`上方 286px 超出单跳且附近无梯子` —— 这种句子一眼就能判断
是"地形真的不允许"还是"我还没实现这个动作"。修完之后 60 例只剩 6 例,
而那 6 例的 reason 全是前者。

顺带这也是第九节(同一个事实只能有一个真源)在移动层的翻版:
"够不够得到"原来在 `is_reachable` 和 `approach` 里各推一遍、阈值还不一样。
现在收敛成一个 `MovePlan`, 单一生产者、两个消费者,
不变量"决策放行的执行一定做得了"和射程的 `engage ⟹ hold` 完全同构。

**后续**:`approach()` 执行 `JUMP_UP` 时原来还要求"先走到 `takeoff_x` 精确对齐(±40px)才起跳"。
这一步本身就在犯同一个错误 ——`takeoff_x` 只是"怪的 x, 检测到平台就微调"这种**估计**,
拿一个估计值去死磕像素级对齐,等于又把"我们的坐标不够准"伪装成了"还没到起跳的时机"。
改成:没对齐就直接边跳边靠近(`edge_jump_up` 带方向起跳,空中会飘一段,本身就在缩小水平差),
对齐了才原地上跳。跳不上去的代价一直是 `JUMP_FAIL_LIMIT` 次尝试,而不再多花几百毫秒走位。

## 十一、日志里看不见的东西,要画出来 / 造实验

这轮的问题,**在日志里一个都看不出来**:

| 问题 | 靠什么发现的 |
|---|---|
| 参考图 0/28 命中 | 单独跑定位器,打印每帧 source 和峰值 |
| 名牌锁到经验条 | 按 HUD 原样把绿框画到帧上,一眼看见框在经验条上 |
| 传送门/鼠标指针被当怪 | 把每个检测框**裁出来拼成一张图**看 |
| 平台漂移 75px | 造受控实验:同一帧平移 35px/帧,对比暴露位置 vs 真实位置 |
| 身份被门控冻住 | 逐帧打印 `confidence/source`,发现位置卡在一个值不动 |
| 怪数偏低是假象 | 对比"原始检测"与"2 帧确认后",发现是样本帧相隔 60s |
| 4px 被当成一层楼 | 打印每条 'down' 边的实际高度差 |

之前几轮一直在调阈值,是因为**看到的是症状不是现场**。
把中间量渲染出来、把检测裁出来、造一个知道真值的实验——
这三招的成本都很低,但它们把"猜"变成了"测"。

顺带一个坑:样本帧是心跳截图,**每帧相隔 60 秒**,不是连续帧。
直接跑会得出"怪数只有 1/4 可用"的错误结论(跨帧匹配接不上,2 帧确认全被滤)。
按实机连续帧模拟(每帧连喂两次)后确认率 100%。
**离线验证前先搞清楚样本的时间结构**,否则会去修一个不存在的 bug。

## 十二、下次改这类东西之前,先问这十二个问题

1. 这个常数描述的是**关系**吗?它依赖的东西会变吗?变了会报错还是静默失效?
2. 这个派生量的更新频率,和它的消费频率一致吗?中间帧消费的是哪一时刻的世界?
3. 这个判定是**身份**(跨帧稳定)还是**观察**(单帧)?谁有权改它?
4. 这个阈值当初为什么是这个值?是不是在补偿别处的 bug?根因修了吗?
5. 同一个事实有几处在算?决策和执行用的是不是同一个函数、同一份数据?
6. 这个现象在日志里能看见吗?看不见的话,画出来要多少行代码?
7. 这个几何判据(大于/小于/重叠)的阈值,大于该量的观测噪声吗?
8. 这里有没有**积分器**(x += ...)?它的锚点是什么?跑一小时会漂多少?
9. 这个阈值是不是同时在管"起批"和"维持"?检测抖动时会不会把能力压成平方?
10. 这个行为"不像人"是缺纹理(节奏)还是缺结构(目标)?问它"你现在想去哪"答得上来吗?
11. 这个"做不到/不可达"的结论, 能说出**为什么**吗?会不会只是我没实现那个动作?
12. 我的验证样本,时间结构和实机一样吗?测试跑得够久吗?
